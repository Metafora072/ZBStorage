# 外存 FUSE 预检发现的并发写文件大小回退

状态：**已复现，未修复；不是 Scheduler 放置或节点迁移已失败。** 归属需由客户端、真实存储节点与 MDS 负责人对齐并发写契约。当前 T03 正式基线采用任务书允许的串行方式，并明确启用 FUSE `-s`；这只是限制测试并发，不是修复。

## 现场

目录：`/mnt/md0/zbstorage_t03_fuse_20260915T042247__qd7p4an/`。

使用当前版本真实 Scheduler、CMS/MDS、真实存储节点及 FUSE，后端位于 `/dev/md0`。Python 用 `O_DIRECT` 打开文件，一次 `pwrite` 写入 5 MiB + 17 bytes（5242897 bytes）。FUSE 默认多线程处理。写系统调用返回全部字节，但随后的 MDS 权威文件属性核对失败，测试以失败退出，未进入迁移。

`migration/client/metrics/io_latency_*.csv` 显示内核把这一次写拆成 6 个回调，起始时间重叠，全部回调返回成功；末尾 65 bytes 的写回调先完成。存储节点持久化的最终记录为：

```text
inode=5, file_size=4194256, object_unit_size=4194304, version=6
last_txid=tx-5-1789446174378-3145680-1048576
```

文件：`migration_cluster/node-real-01/disks/.archive_meta/file_meta/file_meta.tsv`。最终大小 4194256 小于本次成功写入范围 5242897，不能当作正确结果。所有失败现场与日志保留。

## 代码依据及边界

- `FuseWriteImpl` 的 Allocate → 对象写 → Commit → MDS Update 流程没有按 inode 串行化；一个 POSIX 调用可能被内核拆为并发回调，所以“负载发生器并发为 1”不保证“文件元数据提交并发为 1”。
- 真实节点 `ApplyFileMetaInternal` 仅在 `expected_version > 0` 时校验版本；初始元数据不存在时多个计划都可能带版本 0。
- 元数据更新直接采用请求的 `file_size`。后完成的较低偏移分片可能覆盖之前提交的较大文件长度，本次持久化记录体现了这种回退。
- 客户端的 MDS `UpdateInodeStat` 失败路径也没有向写调用返回失败，是需要一起评估的提交一致性问题；不能仅凭 RPC 写字节成功认定文件元数据正确。

可能的修复需要区分普通写入的扩展语义与显式 truncate 的收缩语义，并处理跨客户端并发、版本冲突重试、MDS 更新顺序和错误传播，不能简单把所有元数据更新改为 `max(size)`。本次没有替其他模块重写这套契约。

## 对当前测试结论的影响

开启单线程 FUSE 后，同样的跨对象文件完整写读及排空迁移已在小规模外存预检中通过。后续万文件实验显式保留单线程配置和原始命令；其结果仅覆盖串行基线。

因此，报告必须同时保留“串行真实链路通过”和“多回调并发写发现缺陷”，不得表述为“全系统所有 IO 语义已完善”。
