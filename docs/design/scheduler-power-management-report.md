# Scheduler 节点管理与功耗调度汇报版设计

## 一、建设目标

本设计把 Scheduler 从“心跳与启停控制面”扩展为统一的节点管理、性能建模和功耗调度中心。管理范围包括：

- 存储节点。
- 元数据存储节点。
- 光盘库节点。

Scheduler 统一记录节点容量、设备组成、网络与内部带宽、访问延迟、四级功率、可靠性、加入时间、寿命和退出时间，并维护加入、工作、失效、排空和退休过程。

在真实系统中，Scheduler 根据节点上报的访问指标调节功耗状态；在长期仿真中，同一套策略由 trace 和模拟时钟驱动。最终输出容量、性能、功率、能耗、节点数量和故障变化曲线。

## 二、为什么需要重构与当前进度

重构前 Scheduler 虽已有心跳、健康检测、主备切换、MDS 集群视图和 Start/Stop/Reboot，但存在以下问题：

- 新节点只能通过首次心跳隐式出现，没有正式加入流程。
- 节点只能变成 DEAD，没有删除、排空和退休流程。
- 心跳没有请求数、吞吐、队列、利用率和最近访问时间，无法根据负载调节功耗。
- 现有功耗状态只表达 ON/OFF/STARTING/STOPPING，没有峰值、中值、待机和能耗统计。
- 没有元数据节点类型、寿命、可靠性和长期仿真时间模型。
- 状态在内存中，重启不能恢复长期实验。
- 现有仿真把 10000 解释成 optical node 数量，导师最新说明则更像每个光盘库节点包含 10000 张 DISC，需要统一规模口径。

因此不能只给 optical node 增加一个孤立三态数组，而应建立统一节点模型。

当前前两个实现阶段已经落地统一节点模板、性能公式、寿命抽样、四级功耗和能耗引擎，并提供显式注册、可核验排空/退休、窗口指标、单访问事件和分页查询 RPC。旧心跳节点可以自动进入新模型，Real、Virtual、Optical 和 MDS 已有自动指标生产者，trace 也可以通过 replay 工具驱动同一模型。

managed catalog 已支持版本化快照和启动恢复，模拟节点也已与服务器墙钟隔离并支持显式推进。本阶段又完成了真实对象迁移、MDS 原子位置提交、迁移进度自动退休、容量安全水位、可选物理功耗执行、可靠性故障/修复、批量接口和长期时序输出。当前已经形成从指标/trace 到功耗决策，以及从删除请求到安全迁移和停机的仓库内闭环。

## 三、总体架构

```text
真实节点/MDS 指标 ──┐
trace 与长期事件 ───┼──> Scheduler
管理端加入/删除 ─────┘       |
                              +-- 节点事实表与派生列表
                              +-- 生命周期与失效管理
                              +-- 性能和延迟模型
                              +-- 四级功耗策略
                              +-- 功率与能耗统计
                              +-- 可靠性和寿命模型
                              +-- CMS目录提案
                                      |
                                      v
                         CMS成员/紧凑ID/放置准入权威
                                      |
                                      v
                              MDS真实I/O放置
```

内部只维护一份节点事实表。导师要求的“加入节点列表、工作节点列表、失效节点列表”都从节点状态派生，避免多份列表不一致。

## 四、统一节点状态

每个节点有六个彼此独立的状态维度：

- 健康：HEALTHY、SUSPECT、FAILED。
- 生命周期：JOINING、WORKING、DRAINING、EXITING、RETIRED。
- 功耗：PEAK、MEDIUM、STANDBY、OFF。
- 启停过渡：STABLE、STARTING、STOPPING、REBOOTING。
- 运维准入：ENABLED、DRAINING、DISABLED。
- 服务模式：READ_WRITE、READ_ONLY（主要用于光盘库自动降级）。

工作列表、加入列表、失效列表和退休历史分别由上述状态筛选得到。新数据只能放到健康、正在工作、运维允许、可读写、已唤醒且设备健康的节点。

## 五、三类节点默认模型

### 1. 存储节点

- HDD：默认 `18 TB × 24`，总容量 `432 TB`，允许多个设备组。
- 外部网络：`10 GB/s`。
- 内部并发：5 块盘，每盘 `200 MB/s`，聚合 `1 GB/s`。
- 基础延迟：`5 ms + 文件大小 / 1 GB/s`。
- 功率：峰值 1000 W，中值 300 W，待机 100 W，关闭 0 W。
- 平均寿命：5 年，正态分布。

### 2. 元数据存储节点

- SSD：默认 `4 TB × 16`，总容量 `64 TB`，允许多个设备组。
- 外部网络：`10 GB/s`。
- 内部并发：10 块 SSD，每块 `5 GB/s`；理论聚合 50 GB/s，受外部网络限制后的有效上限为 10 GB/s。
- 基础延迟：`0.5 ms + 文件大小 / 10 GB/s`。
- 功率：峰值 500 W，中值 200 W，待机 50 W，关闭 0 W。
- 平均寿命：5 年，正态分布。

### 3. 光盘库节点

- HDD 缓存：默认 `28 TB × 10`，总容量 `280 TB`。
- DISC：默认每张 1 TB，共10000张，总容量10 PB。
- 外部网络：`10 GB/s`。
- 光驱：10 个，每个 `100 MB/s`，聚合 `1 GB/s`。
- HDD 命中：`0.5 ms + 文件大小 / HDD 有效带宽`。
- 光盘未命中：机械取盘 60 s + 光驱寻道 0.5 s + 文件大小 / 光驱有效带宽。
- 功率：峰值400 W，中值200 W，待机50 W，关闭0 W。
- 平均寿命：10 年，正态分布。

HDD缓存和光驱是两条独立路径：默认HDD缓存为`10 × 28 TB`、每盘`200 MB/s`且并发10；光驱聚合读取`1 GB/s`、写入`100 MB/s`。性能计算按读写方向和访问路径选择带宽。

## 六、性能计算

总容量按全部设备组求和：

```text
总容量 = Σ(单设备容量 × 设备数量)
```

普通访问的有效带宽为：

```text
有效带宽 = min(外部网络带宽, 并发设备数 × 单设备带宽)
```

完整响应时间不能只有固定延迟，还包括：

```text
响应时间 = 排队时间 + 功耗状态恢复时间 + 固定延迟 + 文件大小 / 有效带宽
```

导师给出的公式是节点已工作且无排队时的基础服务时间。批量操作、平均延迟和 P99 实验还需要纳入队列及并发设备数。

## 七、功耗调度

四级功耗含义：

- PEAK：高吞吐、高并发或队列积压。
- MEDIUM：有正常访问，但未达到峰值负载。
- STANDBY：短期空闲，保留快速恢复能力。
- OFF：长期空闲、已排空或已退出。

基础策略为：

```text
高负载                    -> PEAK
有访问                    -> MEDIUM
短期无访问                -> STANDBY
长期无访问且满足容量安全  -> OFF
待机/关闭节点收到访问     -> 唤醒或启动
```

策略需要配置升降级阈值、最短驻留时间、最小在线节点数和容量安全水位，避免频繁开关及误关有数据节点。

功率按节点等级查表，策略口径和物理执行口径分别按时间积分：

```text
累计能耗 += 当前功率 × 持续时间
```

## 八、访问数据从哪里来

真实系统按统计窗口上报：

- 读写请求数和字节数。
- 活跃请求、队列深度和忙碌时间。
- 最近访问时间。
- 可选平均延迟和 P99。

数据节点负责数据 I/O 指标，MDS 负责元数据指标，避免同一请求在 FUSE、MDS 和数据节点重复计数。

仿真 trace 不直接交给 Scheduler。trace 执行器先根据元数据和放置结果把一个文件操作转换成一个或多个节点访问事件，再交给同一个指标与功耗模型。这样导师给出的 trace、自研 trace 和长期宏观 trace 可以共用调度逻辑。

## 九、节点加入、失效与退出

节点加入：

```text
注册和参数校验 -> JOINING -> 心跳/能力确认 -> WORKING -> 可分配
```

节点删除：

```text
删除请求 -> DRAINING -> 停止新分配 -> 数据迁移
         -> EXITING -> 停止节点 -> RETIRED
```

实际迁移顺序固定为：

```text
枚举源节点实际对象 -> 按 inode 聚合全部对象 -> 选择健康且容量足够的目标
-> 分块复制并回读逐字节校验 -> MDS 比较来源位置并原子切换
-> 删除源对象 -> 上报剩余量 -> StopNode -> RETIRED
```

任一步失败都会指数退避。MDS 提交前不删源；提交后的清理可断点重试。遇到无法映射到 inode 的旧式对象 ID 时任务进入 BLOCKED，避免静默丢失无法更新位置的对象。

节点失效后立即从新分配集合移除，加入失效列表，并触发主备切换或恢复。退休节点保留 tombstone，防止旧进程心跳把同一 ID 自动重新注册。

Virtual Pool 要区分“增删进程”和“调整逻辑节点数量”。逻辑节点数量改变会引起 PG 放置变化，必须经过拓扑 generation 和受控迁移。

## 十、可靠性与长期演进

每个节点记录加入时间、抽样寿命、计划退出时间和实际退出时间：

```text
计划退出时间 = 加入时间 + 寿命
```

存储和元数据节点寿命均值为5年、默认标准差1年，光盘库均值10年、默认标准差2年；都使用正态分布下界截断并记录随机种子。浴盆模型还可按早期、稳定期和磨损期FIT安排故障。

真实运行使用墙钟，长期仿真使用可推进的模拟时钟。`RunLongTermSimulation` 可按日、月或其他步长推进多年，MTBF/MTTR 为 0 时禁用随机故障；配置后按持久化随机种子确定性复现，并通过时序接口输出节点数、功率和累计能耗。

## 十一、对现有系统的兼容方式

- 保留当前 ReportHeartbeat、GetClusterView 查询兼容和 Start/Stop/Reboot。
- 增加显式注册、批量加入、排空、退休、指标上报和功耗查询能力。
- Scheduler向CMS发布精简但完整的节点目录提案；CMS提交、分配紧凑ID并持久化后，MDS才更新可分配节点。
- `ClusterState`仅保留旧RPC投影，心跳、健康、资产清单与托管API共用同一个`NodeRecord`事实表。
- 节点状态、能耗和随机种子进入可恢复快照，运行文件放在 SCHEDULER_ROOT。
- CMS已提交目录、紧凑ID及分配游标进入MDS RocksDB；CMS重启不依赖Scheduler发布顺序重新编号。

## 十二、实验输出

前端和实验至少展示：

- 加入、工作、失效、排空、退休节点数量。
- 四个功耗等级节点数量。
- 总容量、可用容量和不可用容量。
- 吞吐率、平均延迟和 P99。
- 当前功率和累计能耗，按节点类型分解。
- 节点故障、唤醒、关闭、迁移和设备换代次数。

所有实验记录配置版本、单位、时间模式和随机种子，保证结果可解释、可复现。

## 十四、当前实现口径

- 光驱寻道按0.5秒，机械取盘按60秒；每库10000张、单盘1 TB。
- 节点功率和容量按一条物理/虚拟/模拟NodeRecord汇总，不自动乘以`logical_node_count`。
- 默认不允许有驻留数据的节点自动OFF；最低在线节点数和容量由部署配置决定。
- MDS当前以metadata managed node注册，但公共结构不要求元数据节点必须与MDS进程同机。

## 十五、汇报总结

重构后的 Scheduler 以统一节点模型为基础，把节点硬件能力、生命周期、访问负载、性能、功耗和可靠性关联起来。它既能管理真实节点，也能驱动长期演进仿真；它向CMS提交运行状态提案，由CMS权威提交后向MDS提供稳定资源视图，同时向实验和前端输出功率、能耗、容量、延迟和节点变化。

该设计的核心不是简单增加几个功耗字段，而是建立“访问负载如何影响节点状态、节点状态如何影响性能与能耗、节点寿命如何影响集群演进”的完整闭环。
