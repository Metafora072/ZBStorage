# 目录头紧凑存储候选方案

> 2026-11-04：本提案已形成 v2 实现，具体差异和当前限制见 [v2 设计](lhm-v2-design.md)。以下保留原始讨论记录，容量数字为当时字段假设。

记录日期：2026-11-02。状态：讨论方案，尚未实施，不是现有格式说明。

## 目标与选择

将“每目录独占 16 KiB 头块”改成“多个目录头记录共享一个 16 KiB 块”。保留底层固定块 I/O，以块号和槽位定位目录记录；外层 NamespaceStore 接口尽量不变。仅缩小 C++ 结构体但仍分配整个块不能节约磁盘。

512 B 是候选记录大小，不是已确定的磁盘格式。假设块头、位图等合计预留 512 B，则每块容纳 floor((16384-512)/512)=31 条，平均每目录约 528.5 B。

| 目录规模 | 当前目录头占用 | 候选共享布局 |
|---|---:|---:|
| 32,427,097,000 | 约 483.20 TiB | 约 15.59 TiB |
| 1,621,354,850（前者 1/20） | 约 24.16 TiB | 约 0.78 TiB |

仅为目录头的满装容量估算，不包含文件 inode、文件名桶、块碎片及构建临时空间；不能当作整体容量或性能实测。

## 候选字段与需改动的位置

目录记录需容纳目录 inode、父目录持久引用、目录项/文件桶索引描述符等。名称存储及扩展空间必须按实际编码核算；公共块信息由多个记录共享。

改造涉及：目录记录分配与槽位管理；目录 ID/引用编码；按 ID 读取；目录索引元信息；创建、改名、删除、扫描、批量导入中所有“目录对应独占头块”的假设。旧文件不能直接按新布局解释，需显式版本契约。

目录持久父子关系和文件索引描述符应与后续重开方案一并设计，避免紧凑布局完成后再修改一次格式。

## 文件桶单独处理

目录头共享并不会消除“一个含少量文件的目录仍独占 16 KiB 文件桶”的浪费。后续评估多个小目录共享目录项页，或使用可内联少量目录项的记录格式；大目录继续扩展独立桶。不能直接把整块 payload 内联方案和 512 B 紧凑记录视作同一种格式。

## 验收与范围

先测试多个目录共块、槽位边界、ID 唯一性、属性隔离、增删改和遍历，再测真实目录分布下的页面利用率。目录数减少改变工作负载结构，须与原模板区分。重开、异常恢复、批次追加仍是独立能力，不因本方案自动实现。
