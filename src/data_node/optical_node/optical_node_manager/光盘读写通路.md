- # 客户端与真实光盘库节点的文件读取设计

  ## 1. 设计起点与范围

  **设计起点：客户端已经按照原有流程，从元数据服务取得了目标光盘文件的元数据。** 获取元数据的流程不变，不增加或重新设计客户端与元数据服务的交互。

  本文只设计后续两端之间的读取过程：

  ```text
  客户端持有文件元数据
      → 通过异步文件准备接口向真实光盘库提交请求
      → 光盘库后台准备文件并主动通知客户端
      → 应用通过标准 POSIX 接口读取原路径
      → 客户端从光盘库同步取得已准备的真实数据
      → 读取结束后释放相关资源
  ```

  **对外采用“异步文件准备接口＋标准 POSIX 读取接口”。** 应用新增读取前的 `prepare_read` 和整项工作结束后的 `release_prepared`；中间继续使用 `open/read/pread/close`。准备任务、通知会话和光盘读会话均由客户端内部管理，不要求应用直接调用光盘 RPC。

  对外接口用文件路径，内部数据组件用已经取得的文件元数据。路径到元数据的对应沿用现有流程；本文只补充客户端对外使用方式和数据通路，不新增元数据服务协议。

  光盘写入、归档迁移、仿真节点、调度管理和其他模块的协作不在本文范围内。

  正常运行假设：

  - 客户端和光盘库正常运行，网络始终连通，通知正常送达。
  - 文件存在，位置和内容在准备、读取期间保持不变。
  - 光盘库缓存空间充足，后台准备和读取均正常完成。
  - 调用方按“准备 → 收到就绪通知 → 打开读取 → 关闭 → 释放准备结果”的顺序使用。

  不设计断线、重连、重复通知、重试、崩溃恢复、租约或超时回收机制。文件范围、EOF 和缓存引用属于正常读取功能，仍需明确。

  ## 2. 客户端已有的输入

  客户端将已经取得的信息整理为本地 `OpticalFileInfo`，作为数据读取组件的输入，无须为此增加元数据服务接口。

  | 信息 | 用途 |
  | --- | --- |
  | `node_address` | 真实光盘库节点的数据服务地址 |
  | `inode_id` | 目标文件的稳定身份 |
  | `disk_id` | 文件所在光盘标识 |
  | `image_id` | 文件所在镜像标识 |
  | `file_size` | 文件逻辑大小，用于读取范围与结果核对 |
  | `file_version`（已有时携带） | 原样保存已有版本信息，用于关联本次读取；本阶段不设计版本变化处理 |

  原有路径或客户端文件上下文可以保留在本地，用来把就绪事件和后续读取对应到同一个文件。光盘库根据盘片、镜像和文件身份定位数据，不要求客户端提供服务端本地缓存路径。

  ## 3. 核心方案：异步准备、主动通知、同步取数

  ### 3.1 准备阶段

  客户端提交 `PrepareRead` 后，光盘库只完成任务登记和入队，立即返回任务编号。后台再执行排队、装载光盘、读取镜像以及必要的解压，生成可按文件偏移读取的完整文件缓存。

  **整个文件已经可读时，光盘库主动推送 `ReadReady`。** 客户端不定时查询任务状态，也不在某个 POSIX 读取调用中等待数小时。

  ### 3.2 读取阶段

  收到就绪事件后，客户端先记录文件可用并通知应用。应用随后执行标准 POSIX open，由客户端内部获取光盘读会话；read/pread 再按 `offset + size` 发起同步读取。此时数据源是光盘库自己的磁盘缓存，读取 RPC 不再等待取盘或解压。

  文件内容通过普通读 RPC 传输。客户端不必先下载整个文件到本机，准备结果也不通过通知连接传送。

  ### 3.3 两端职责

  | 端 | 工作 |
  | --- | --- |
  | 客户端 | 接受已有元数据、建立通知通道、提交准备、维护本地请求记录、接收就绪事件、向调用方发出本地通知、执行同步读取与释放 |
  | 真实光盘库 | 定位文件、执行后台准备、固定可读缓存、发送就绪通知、管理读会话、提供真实区间数据、释放缓存 |

  客户端的通知接收和任务管理放在现有客户端进程内；光盘库复用现有后台读取引擎。

  ## 4. 完整调用流程

  ```mermaid
  sequenceDiagram
      participant A as 应用 / 配套准备工具
      participant C as 客户端
      participant O as 真实光盘库服务
      participant B as 后台读取引擎与磁盘缓存
  
      Note over C: 已持有目标文件元数据
      A->>C: prepare_read(path, on_ready)
      C->>O: SubscribeReadEvents（首次使用该节点时）
      O-->>C: 通道建立，返回 session_id
      C->>C: 创建 request_id 和本地请求记录
      C->>O: PrepareRead(session_id, request_id, 文件定位信息)
      O-->>C: task_id，已受理
      C-->>A: PrepareHandle，提交调用结束
      Note over A: 可继续处理其他工作
  
      O->>B: 后台准备完整文件
      Note over B: 排队、取盘、读取、必要的解压
      B-->>O: 文件缓存已经可读
      O->>O: 固定准备结果，设置 READY
      O-->>C: 通知流推送 ReadReady(request_id, task_id)
      C->>C: 更新文件的 READY 索引
      C-->>A: on_ready(PreparedFile)
  
      A->>C: POSIX open(path)
      C->>O: AcquireReadSession(task_id)
      O-->>C: read_handle、file_size、max_read_bytes
      C-->>A: 普通文件描述符 fd
      loop 同步读取文件区间
          A->>C: POSIX read / pread
          C->>O: ReadPreparedFile(read_handle, offset, size)
          O->>B: 读取文件缓存的指定区间
          B-->>O: 真实字节数据
          O-->>C: data、bytes_read、eof
          C-->>A: 实际读取字节
      end
  
      A->>C: POSIX close(fd)
      C->>O: ReleaseReadSession(read_handle)
      O-->>C: 读会话已关闭
      A->>C: release_prepared(PrepareHandle)
      C->>O: ReleasePreparedRead(task_id)
      O->>B: 无读取引用后清理本次准备产物
      O-->>C: 准备引用已释放
  ```

  ## 5. 主动通知的实现方式

  ### 5.1 使用 brpc Stream

  项目已有 brpc，建议使用仓库所带的 Streaming RPC 建立通知通道：

  1. 客户端向目标光盘库调用 `SubscribeReadEvents`，同时发起 Stream 建立。
  2. 光盘库接受 Stream，返回 `session_id`，保存会话与 Stream 的对应关系。
  3. 后续准备任务携带该 session_id。
  4. 光盘库在任务 READY 时向 Stream 写入 `ReadReady` 消息。
  5. 客户端接收回调更新本地请求状态，并通过本地事件或回调通知调用方。

  根据仓库内 brpc 文档，Stream 由客户端发起，使用一次 `baidu_std` 协议 RPC 建立，随后服务端可主动写入消息。建立通道的 RPC 立即结束，通知通道持续保留；不把订阅或准备 RPC 挂起数小时。

  一个客户端与一个光盘库之间复用一条通知通道，支持多个准备任务。长时间没有通知是正常现象，本阶段不因空闲而主动关闭连接；客户端正常结束后关闭通道。

  ### 5.2 本地事件衔接

  客户端在发送准备请求之前就创建 `request_id` 和记录，光盘库完成通知绑定后再开始准备。即使准备很快完成，客户端也能凭 request_id 找到对应任务。

  准备响应表示“已受理”，完成事件表示“可读取”。两者在正常并发处理中可能先后被不同线程处理，因此收到受理响应不能覆盖已经记录的 READY 状态。

  调用方等待本地结果时，任务管理器先检查是否已经 READY，未就绪才登记等待。状态检查与等待登记统一管理，确保已经到达的通知不会使调用方错过完成状态。

  本地等待由事件唤醒，不循环发送查询 RPC；本阶段也不设计光盘状态轮询接口或通知确认接口。

  ## 6. 标识和状态

  | 标识 | 含义 |
  | --- | --- |
  | `PrepareHandle` | 对外返回的不透明准备句柄，映射到客户端的 request_id；不是 POSIX fd，也不是光盘 read_handle |
  | `client_id` | 当前客户端实例 |
  | `session_id` | 光盘库为通知通道分配的会话标识 |
  | `request_id` | 客户端生成的准备请求编号，用于关联响应和完成事件 |
  | `task_id` | 光盘库分配的后台准备任务编号 |
  | `read_handle` | 一次打开读取对应的会话，可进行多次区间读取 |
  | `inode_id` | 从已有元数据取得的文件身份 |

  客户端保存光盘库服务地址，task_id 和 read_handle 均在对应光盘库内解释；不同节点的同名编号不能混用。

  准备任务正常状态为：

  ```text
  ACCEPTED → PREPARING → READY → RELEASED
  ```

  - `ACCEPTED`：任务及通知关系已建立。
  - `PREPARING`：排队、装载、读取或解压。
  - `READY`：完整文件可按任意合法区间读取，准备产物已固定。
  - `RELEASED`：准备引用与所有读取引用都已释放，可清理本次产物。

  客户端只需保存“已提交、已就绪、已释放”，不轮询服务端内部准备进度。

  ## 7. 客户端与光盘库接口

  以下为功能级约定，具体 Proto 类型和编号由武家浩、马崇文共同确定。普通 RPC 使用项目统一状态字段；表中重点描述成功路径。

  | 接口 / 消息 | 方向 | 主要输入 | 输出或作用 |
  | --- | --- | --- | --- |
  | `SubscribeReadEvents` | 客户端 → 光盘库 | client_id，附带 Stream 建立 | session_id，建立后立即返回 |
  | `PrepareRead` | 客户端 → 光盘库 | session_id、request_id、inode_id、disk_id、image_id、file_size，已有时附带 file_version | request_id、task_id、已受理；任务入队后立即返回 |
  | `ReadReady` | 光盘库 → 客户端的 Stream 消息 | request_id、task_id、inode_id、file_size，已有时附带 file_version | 告知完整文件已经进入可读缓存 |
  | `AcquireReadSession` | 客户端 → 光盘库 | task_id | read_handle、file_size、max_read_bytes，并增加读取引用 |
  | `ReadPreparedFile` | 客户端 → 光盘库 | read_handle、offset、size | data、bytes_read、eof |
  | `ReleaseReadSession` | 客户端 → 光盘库 | read_handle | 关闭本次读会话，减少读取引用 |
  | `ReleasePreparedRead` | 客户端 → 光盘库 | task_id | 释放本轮准备引用，不再允许为该任务创建新会话 |

  ### 7.1 PrepareRead 与 ReadReady

  PrepareRead 按整文件准备，不携带文件内容，不要求客户端知道光盘库本地路径。返回 task_id 只表示受理，不表示文件可读。

  ReadReady 是服务端主动消息，不是客户端请求。必须在必要的读取和解压完成后发送；只有盘片已装载或镜像已缓存时，不能提前通知文件就绪。

  一个客户端可提交多个文件任务，每个任务分别返回就绪事件。客户端按 request_id 关联到已有的文件上下文。

  ### 7.2 读取会话

  每次开始一次独立读取会话时调用 AcquireReadSession。一个准备任务可以创建多个读会话，每个会话有独立 read_handle。

  读取接口使用显式 offset，不在服务端维护隐式文件游标。普通 read 的游标由客户端/POSIX 文件层处理，pread 的位置直接来自调用参数。

  ### 7.3 区间读取规则

  - offset 是**目标文件内的绝对偏移**，不使用镜像偏移、压缩数据偏移或对象内偏移。
  - size 为 0 时返回 0 字节，不因这次调用改变任务状态。
  - offset 位于文件末尾或之后时返回 0 字节和 EOF。
  - 正常非空读取长度为 `min(size, file_size - offset)`，返回的 bytes_read 必须等于 data 长度。
  - eof 表示本次读取已达到文件末尾；它不表示关闭会话或释放缓存。
  - 大于 max_read_bytes 的上层请求由客户端拆分为多次 RPC，下一片偏移按实际完成字节推进。
  - 支持顺序读、随机读、重复读，以及先读文件尾再读文件头。
  - 返回的是实际文件内容，不使用零或占位字符补齐尚未读到的数据。

  ## 8. 缓存保持和释放

  真实文件准备在光盘库自己的磁盘缓存中完成。第一版可沿用“每个准备任务一个可读文件产物”，不要求新增跨客户端缓存合并机制。

  采用两种引用：

  | 引用 | 建立时机 | 释放时机 |
  | --- | --- | --- |
  | 准备引用 | 文件准备完成、发送 ReadReady 之前 | ReleasePreparedRead |
  | 读取引用 | 每次 AcquireReadSession | 对应 ReleaseReadSession |

  准备引用保证通知到达后，文件仍然可以被打开，也支持同一文件多次打开。读取引用保证一次已经开始的读会话可以正常结束。

  只要任一引用存在，本次文件产物就保留。准备引用释放后不再创建新读会话，已有会话可以继续读取；引用全部归零后才清理产物。共享镜像的原有缓存管理独立保留，不能因释放一个文件产物就删除其他文件仍在使用的镜像。

  **读到最后一片或 EOF 时不能删除缓存。** 释放必须由明确接口驱动；本阶段使用方正常结束读取后显式释放，不增加租约或自动超时回收。

  ## 9. 对外接口与客户端内部接入

  ### 9.1 对应用提供的接口

  对外仅新增异步准备和显式释放两项能力，文件读取继续使用标准 POSIX 接口。建议先提供一个客户端 SDK，接口如下，名称及类型为待实现约定：

  ```cpp
  // 不透明类型，仅用于管理一次文件准备结果；内部表示在此省略。
  struct PrepareHandle { /* SDK 内部表示 */ };
  
  struct PreparedFile {
      PrepareHandle handle;
      std::string path;      // 原 ZBStorage 挂载路径，不是缓存文件路径
      uint64_t size;         // 已准备文件的大小
  };
  
  PrepareHandle prepare_read(
      const std::string& path,
      std::function<void(const PreparedFile&)> on_ready);
  
  void release_prepared(PrepareHandle handle);
  ```

  | 对外接口 | 使用约定 |
  | --- | --- |
  | `prepare_read(path, on_ready)` | path 为该 ZBStorage 挂载下的文件路径；请求被接受后返回 PrepareHandle，不等待光盘准备完成；就绪后在 SDK 的回调执行上下文调用 on_ready |
  | `on_ready(PreparedFile)` | 回调发生前，FUSE 客户端已把该文件标记为可读取；调用方随后可以使用 ready.path 执行 open；回调只投递工作，不在通知接收线程中长时间处理数据 |
  | `open/read/pread/close` | 标准 POSIX 调用，路径和原文件一致；客户端内部负责建立光盘读会话、取数和关闭会话 |
  | `release_prepared(handle)` | 表示整项工作不再需要该准备结果；正常使用时先关闭相关 fd，再调用释放；内部映射到 ReleasePreparedRead |

  PrepareHandle 不能交给 read，光盘 task_id/read_handle 也不能作为 POSIX fd。应用不需要知道光盘编号、镜像编号、节点地址或任何内部 RPC。

  文件状态和对外行为约定如下：

  | 时刻 | 对外行为 |
  | --- | --- |
  | 准备中 | prepare_read 已返回，应用可以做其他工作；不应开始普通文件读取 |
  | 收到 on_ready 后 | 可以通过原挂载路径 open，再同步 read/pread |
  | 一次 close 后 | 只结束该次打开；准备结果仍保留，可再次 open |
  | release_prepared 后 | 该准备句柄不再用于新打开；已有读取引用归零后可清理缓存；下一轮访问重新准备 |

  若调用方提前打开未就绪的光盘文件，客户端尽快返回项目约定的“未准备”结果，FUSE 层建议映射为 EAGAIN，不在 open/read 内等待数小时。普通程序不保证自动处理这一约定，因此通过预先准备再启动程序来使用本方案。

  ### 9.2 SDK 使用示例

  下面是正常场景的 C++ 风格伪代码；Client、PrepareHandle、事件队列及 process 均为示意，当前尚未实现。

  ```cpp
  // SDK 连接到管理 /mnt/zb 这一挂载的 FUSE 客户端。
  Client client("/mnt/zb");
  WorkQueue<PreparedFile> ready_queue;
  
  auto handle = client.prepare_read(
      "/mnt/zb/archive/data.bin",
      [&](const PreparedFile& ready) {
          ready_queue.push(ready);
      });
  
  // prepare_read 已返回，当前程序可以继续其他工作。
  ```

  应用的工作线程收到本地就绪事件后，使用原有 POSIX 数据处理代码：

  ```cpp
  PreparedFile ready = ready_queue.pop();  // 本地事件等待，不查询光盘库
  
  int fd = open(ready.path.c_str(), O_RDONLY);
  char buffer[1024 * 1024];
  ssize_t n;
  while ((n = read(fd, buffer, sizeof(buffer))) > 0) {
      process(buffer, n);
  }
  
  close(fd);
  client.release_prepared(ready.handle);
  ```

  需要随机读取时改用标准 pread 即可，不需要再次提交准备请求。示例按本文假设省略异常处理。

  ### 9.3 未修改的普通程序如何使用

  对 cat、cp 或已有 POSIX 程序，提供客户端配套准备命令，先准备文件再启动原程序。建议命令如下，均为待实现接口：

  ```bash
  # 提交后立即返回 prepare_id。
  zbctl stage submit /mnt/zb/archive/data.bin
  
  # 等待 FUSE 客户端收到完成通知；不轮询光盘库。
  zbctl stage wait <prepare_id>
  
  # 文件就绪后，普通程序使用原路径读取。
  cat /mnt/zb/archive/data.bin
  # 或 ./existing_program /mnt/zb/archive/data.bin
  
  # 本轮工作全部结束后，释放准备结果。
  zbctl stage release <prepare_id>
  ```

  wait 是使用方显式选择等待的控制命令，等待期间可以长时间存在，但不会占用一个等待光盘准备的 POSIX 文件读取调用。也可以先提交后去处理其他工作，再运行 wait；若文件已就绪，它立即返回。

  submit 命令退出后，准备任务和通知通道由持续运行的 FUSE 客户端进程持有。后续 wait 命令和普通读取程序可以是不同进程，只需使用同一挂载实例。prepare_id 是 PrepareHandle 的命令行表示，可包含挂载实例信息或由工具映射到对应客户端，不能只按一个全局假定唯一的整数查找任务。

  ### 9.4 SDK、命令与 FUSE 共用一份准备状态

  SDK 和命令都通过本地控制通道连接管理相应挂载的 FUSE 进程，建议使用每个挂载一个 Unix domain socket。该通道属于客户端内部功能，不增加独立守护进程，也不增加其他服务的接口。

  本地控制通道只需要三种操作：

  | 本地操作 | 功能 |
  | --- | --- |
  | 提交准备 | 接收路径，利用既有文件上下文取得第 2 节的信息，调用内部准备组件，返回 PrepareHandle |
  | 订阅准备完成 | SDK 注册回调，或 wait 命令等待本地事件；若已 READY，立即交付结果；正常路径不轮询光盘库 |
  | 释放准备结果 | 将 PrepareHandle 映射到目标节点和任务，调用 ReleasePreparedRead |

  SDK 的 prepare_read 将提交与本地完成订阅封装为一次调用。光盘 Stream 终止于 FUSE 进程，SDK 接收的是本地事件，由 SDK 调用应用的 on_ready。

  业务程序通过 POSIX 打开文件时并不会传入 PrepareHandle。因此必须由 FUSE 进程维护“文件身份 → 已准备任务”的索引，在 open 时自动匹配。准备状态不能只保存在 SDK 进程或一次命令的内存中，否则普通程序无法使用。

  本阶段约定：同一挂载实例中，一个文件同一版本只保留一个有效准备句柄，准备期间不重复提交；该准备结果可供多个正常打开共享。文件身份采用既有 inode 及已有时的版本，路径用于对外展示；不增加文件变化处理机制。

  ### 9.5 客户端数据组件与内部映射

  对外接口接入后，内部数据组件仍以已取得的 OpticalFileInfo 为起点，不重设计获取元数据的过程。应用调用、内部动作与光盘 RPC 的对应关系如下：

  | 应用或工具动作 | 客户端内部动作 | 光盘接口 |
  | --- | --- | --- |
  | prepare_read / stage submit | 接受已有文件信息，创建本地请求和准备句柄，绑定通知通道 | SubscribeReadEvents（按需一次）、PrepareRead |
  | on_ready / stage wait 返回 | 收到通知后先发布 READY 索引，再交付本地事件 | 接收 ReadReady，不发送状态查询 |
  | POSIX open | 根据文件身份找到 READY 任务，为本次打开创建读上下文 | AcquireReadSession |
  | POSIX read / pread | 从文件上下文取得光盘 read_handle，按文件偏移读取 | ReadPreparedFile |
  | POSIX close | 释放本次打开的读取引用 | ReleaseReadSession |
  | release_prepared / stage release | 撤销该准备结果对新打开的可用性，释放准备引用 | ReleasePreparedRead |

  需要保存的本地记录：

  | 本地记录 | 内容 |
  | --- | --- |
  | 通知连接表 | 光盘库地址 → Stream、session_id |
  | 准备请求表 | PrepareHandle/request_id → file_info、task_id、状态、本地事件接收者 |
  | 已准备文件索引 | 挂载实例、inode、已有时的版本 → READY 准备请求 |
  | 读取上下文 | FUSE 文件句柄 → 光盘库地址、read_handle、文件大小、所属准备请求 |

  prepare_read 在发请求前登记本地记录；收到 ReadReady 后，先完成任务和文件索引更新，再通知应用。应用因此可以在 on_ready 之后立即调用 open。

  ### 9.6 与现有 FUSE 操作的衔接

  本方案只改变已识别为光盘文件的数据访问分支，已有元数据获取和文件管理流程保持原样：

  1. **准备阶段**：对外 prepare_read 将现有元数据交给内部准备组件，发送异步请求；FUSE 读操作不承担这一阶段。
  2. **准备完成**：接收通知，发布 READY 文件索引并唤醒本地调用方；此时先不创建某次 open 专属的读会话。
  3. **FuseOpen**：利用已有文件身份查找 READY 索引，再获取光盘 read_handle 并关联原有客户端文件句柄。未就绪时立即结束本次打开，不等待准备。
  4. **FuseRead**：复用该次打开的读会话，以文件绝对偏移执行区间 RPC；处理请求拆分、实际返回长度和 EOF，不准备或轮询。
  5. **FuseRelease**：释放对应读取会话，清除本次读上下文，准备结果继续保留。
  6. **显式准备释放**：关闭相关文件之后，调用 release_prepared；移除 READY 索引并通知光盘库释放准备引用。已存在的读上下文保持独立，直到正常关闭。

  对单独打开的每个文件建立独立读会话；同一打开引用的正常复制或继承沿用既有 FUSE 文件句柄生命周期，不因某个描述符关闭就提前释放其他引用仍在使用的会话。

  现有磁盘读取分支不改动。客户端取得元数据的方式不属于这次接口改造。

  ## 10. 光盘库内部接入

  复用现有异步读取引擎，增加以下功能：

  1. **通知会话表**：保存 session_id 与 Stream 的映射。
  2. **任务上下文**：在读取任务中记录 request_id、session_id 和文件身份；后台任务入队前绑定通知目标。
  3. **完成通知**：现有后台任务生成可读文件后建立准备引用，设置 READY，再主动发送 ReadReady。
  4. **读会话表**：保存 read_handle → task_id、文件缓存路径、文件大小。
  5. **同步区间读取**：复用现有文件产物读取函数，按文件绝对偏移返回真实内容。
  6. **显式释放**：移除“末片读取成功后自动删除产物”的逻辑，按准备引用和读取引用清理。

  光盘节点自行完成排队、装载、介质读取和解压，客户端只提交文件定位信息、接收就绪通知和取回数据。

  ## 12. 双方实施顺序与验收

  ### 12.1 实施顺序

  1. 武家浩、马崇文确认文件定位字段、通知消息、文件偏移、会话和释放语义，并明确对外准备接口与 POSIX 操作的映射。
  2. 马崇文将现有后台准备结果接到 ReadReady 通知；武家浩实现订阅和本地完成回调。
  3. 马崇文实现读会话、区间读取和显式释放；武家浩实现对应 RPC 封装。
  4. 武家浩把数据组件接入已经取得元数据的客户端光盘分支，建立文件身份到 READY 任务的索引，使正常 open/read/pread/close 自动使用内部读会话。
  5. 武家浩实现 SDK、配套准备命令和客户端进程内控制通道，使业务程序可以直接使用回调或“先准备、再运行普通程序”的方式。
  6. 双方使用已知文件元数据和真实光盘库完成以下正常场景测试。

  ### 12.2 验收场景

  | 场景 | 验收标准 |
  | --- | --- |
  | 元数据作为既有输入 | 直接使用已取得的 node_address、inode_id、disk_id、image_id 和大小启动流程，无新增其他模块交互 |
  | 异步准备 | PrepareRead 入队后即返回，调用方可以继续其他工作 |
  | 主动通知 | 准备完成后接收 ReadReady；整个等待期间没有查询状态的轮询 RPC |
  | SDK 与 POSIX 组合 | prepare_read 返回后程序可继续工作；on_ready 后通过原路径调用标准 open/read/pread/close，应用不直接调用光盘 RPC |
  | 准备工具与普通程序组合 | stage submit 退出后任务仍由 FUSE 进程持有；stage wait 由本地事件唤醒，随后 cat 或现有程序可通过同一挂载读取原文件 |
  | 准备状态与打开匹配 | 普通 open 不携带 PrepareHandle，FUSE 仍能按文件身份匹配正确 READY 任务；不同打开获得各自读取会话 |
  | 完整文件读取 | 收到通知后分片读回，大小和内容与已知原文件一致 |
  | 随机与重复读取 | 先读尾部再读头部、重复读同一区间，均返回真实内容，文件缓存不因末片读取被清理 |
  | 请求拆分与 EOF | 超过 max_read_bytes 的请求正确拼接，末尾裁剪和 EOF 正确 |
  | 多个读取会话 | 同一准备结果支持多个独立读会话，关闭一个会话不影响其他会话 |
  | close 与准备释放分离 | close 后可再次 open 而不重新取盘；release_prepared 后撤销新打开可用性，引用归零后清理缓存 |
  | 多文件通知 | 同一通知通道可接收多个准备任务的完成事件，并关联正确的本地请求 |
  | 资源释放 | 关闭读取会话并显式释放准备引用后，本次文件产物正常清理 |

  可记录“提交准备至收到通知的时间”和“就绪后的读取时间/字节数”，用于确认两个阶段按设计分离。本阶段不扩展其他模块的指标系统，也不加入异常场景测试。
