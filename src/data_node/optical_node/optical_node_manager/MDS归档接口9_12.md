- - # MDS 文件归档接口设计（简化版）

    ## 1. 目标和范围

    MDS 定时选择若干个目录子树，把其中需要归档的文件信息发送给一个光盘库节点。光盘库节点完成两个阶段：

    1. 将文件打包为镜像并保存在磁盘上，向 MDS 上报文件与镜像的对应关系。
    2. 将镜像刻录到光盘上，向 MDS 上报镜像与光盘的对应关系。

    本版只考虑正常流程，并做以下假设：

    - 除归档节点读取文件内容外，被选中的文件在归档期间不会被业务读写、删除、移动或重命名。
    - 一个光盘库节点同一时间只处理一个归档批次。
    - 元数据分片按顺序到达，不考虑丢失、重传和恢复。
    - 每个文件只位于一个数据节点，没有副本和 PG。
    - 一个文件不跨镜像，一个镜像只刻录一份。
    - 文件原有目录结构继续由 MDS 管理，光盘库节点不保存目录元数据和目录关系。

    当前 MDS 是 namespace 和 inode 元数据的权威节点，但不保存文件内容：[src/mds/README.md](/home/wjh/ZBStorage/src/mds/README.md:3)。新接口继续使用项目现有的 protobuf/brpc 形式和 `MdsStatus`：[src/msg/mds.proto](/home/wjh/ZBStorage/src/msg/mds.proto:1)。项目中现有的 Archive 和 Optical 代码不作为本设计的参考。

    ## 2. 归档文件信息

    MDS 只向光盘库节点发送读取和打包文件所必需的字段：

    ```protobuf
    message ArchiveFile {
      uint64 inode_id = 1;

      //从real_node下载文件数据所需最小字段集
      uint64 size = 2;
      uint64 object_unit_size = 3;
      string target_node_id = 4;
      string target_disk_id = 5;
    }
    ```

    字段说明：

    - `inode_id` 用于两次上报后更新 MDS 元数据，也可以作为文件在镜像中的内部标识。
    - `size` 用于读取文件和安排镜像空间。
    - `object_unit_size` 文件的分片大小。
    - `target_node_id` 目标热数据节点id，通过id到scheduler中查询具体node_address。
    - `target_disk_id` 目标文件所在的磁盘位置，用于定位文件。

    目录名称、父子关系、权限和时间等权威元数据仍保存在 MDS 中，不发送给光盘库节点。

    ## 3. MDS 向光盘库节点发送文件信息

    光盘库节点提供一个 RPC：

    ```protobuf
    message SendArchiveMetadataRequest {
      uint64 batch_id = 1;
      repeated ArchiveFile files = 2;
    }
    
    message ArchiveReply {
      MdsStatus status = 1;
    }
    
    service OpticalNodeService {
      rpc SendArchiveMetadata(SendArchiveMetadataRequest)
          returns (ArchiveReply);
    }
    ```
    - batch_id仅用于后续可能实现的任务查询接口，光盘节点本身不关系批次，封装打包以文件为单位，逐个从热数据节点下载文件并进行封装。
    - 由于仅传输归档必要元数据，数据量较小，无需

    当前不需要 `Begin`、`Commit`、分片补传或任务查询接口。

    ## 4. 光盘库节点调用的 MDS 接口

    `image_id` 和 `disc_id` 均由 MDS 统一分配，光盘库节点不再自行生成。MDS 保证分配的 ID 全局唯一：光盘库节点在生成镜像前申请 `image_id`，在刻录前申请 `disc_id`。

    两个 ID 的实际取值都是 MDS 分配的全局唯一 `uint64`，对外传输时包装为字符串：

    - `image_id`：`img-<seq>`
    - `disc_id`：`disc-<seq>`

    其中 `<seq>` 为 MDS 分配的 uint64 唯一值。MDS 只把 ID 当作不透明字符串保存，不解析其格式。

    ### 4.1 分配 ID：光盘库节点 -> MDS

    光盘库节点按需调用下面的接口申请 ID：请求携带申请方信息，返回值为可用的 ID 字符串。两个接口按存储层次分开定义。

    disc 层（光盘介质）：

    ```protobuf
    message AllocateAvailableDiscIdRequest {
      string node_id = 1;
      string node_address = 2;
      uint64 allocate_ts_ms = 3;
    }

    message AllocateAvailableDiscIdReply {
      MdsStatus status = 1;
      string disc_id = 2;
    }

    service MdsService {
      rpc AllocateAvailableDiscId(AllocateAvailableDiscIdRequest)
          returns (AllocateAvailableDiscIdReply);
    }
    ```

    image 层（镜像）：

    ```protobuf
    message AllocateAvailableImageIdRequest {
      string node_id = 1;
      string node_address = 2;
      uint64 allocate_ts_ms = 3;
    }

    message AllocateAvailableImageIdReply {
      MdsStatus status = 1;
      string image_id = 2;
    }

    service MdsService {
      rpc AllocateAvailableImageId(AllocateAvailableImageIdRequest)
          returns (AllocateAvailableImageIdReply);
    }
    ```

    - `node_id` / `node_address` 用于标识申请方（光盘库节点）。
    - `allocate_ts_ms` 为本次分配的时间戳，供 MDS 记录分配时刻。
    - 返回值为可用的 ID 字符串：`disc-<seq>` / `img-<seq>`，其中 `<seq>` 为全局唯一的 uint64。

    ### 4.2 第一次上报：文件已打包到镜像

    ```protobuf
    message ReportFilesPackedToImageRequest {
      string node_id = 1;
      string image_id = 2;
      repeated uint64 inode_ids = 3;
    }
    ```

    MDS 收到后：

    1. 记录 `image_id -> node_id` 的所属关系。
    2. 建立 `inode_id -> image_id` 关系。
    3. 将对应文件状态更新为 `ARCHIVE_IMAGE_READY`。

    ### 4.3 第二次上报：镜像已刻录到光盘

    ```protobuf
    message ReportImagesBurnedToDiscRequest {
      string node_id = 1;
      string disc_id = 2;
      repeated string image_ids = 3;
    }
    ```

    一张光盘可以包含一个或多个镜像。刻录完成后，光盘库节点上报一次。MDS 收到后：

    1. 记录 `disc_id -> node_id` 的所属关系。
    2. 建立 `image_id -> disc_id` 关系。
    3. 通过镜像找到对应文件。
    4. 将对应文件状态更新为 `ARCHIVE_COMPLETED`。

    第二次上报不再传递 `inode_id`，因为文件与镜像的关系已经在第一次上报中建立。

    ### 4.4 MDS RPC 汇总

    ```protobuf
    service MdsService {
      // 现有 RPC ...

      rpc AllocateAvailableDiscId(AllocateAvailableDiscIdRequest)
          returns (AllocateAvailableDiscIdReply);

      rpc AllocateAvailableImageId(AllocateAvailableImageIdRequest)
          returns (AllocateAvailableImageIdReply);

      rpc ReportFilesPackedToImage(ReportFilesPackedToImageRequest)
          returns (ArchiveReply);
    
      rpc ReportImagesBurnedToDisc(ReportImagesBurnedToDiscRequest)
          returns (ArchiveReply);
    }
    ```

    ## 5. MDS 中的最小归档信息

    文件只需要三个归档状态：

    ```protobuf
    enum FileArchiveState {
      ARCHIVE_PENDING = 0;
      ARCHIVE_IMAGE_READY = 1;
      ARCHIVE_COMPLETED = 2;
    }
    
    message FileArchiveInfo {
      FileArchiveState state = 1;
      string image_id = 2;
      string disc_id = 3;
    }
    ```

    状态变化如下：

    ```text
    ARCHIVE_PENDING
        -> ARCHIVE_IMAGE_READY      // 第一次上报
        -> ARCHIVE_COMPLETED        // 第二次上报
    ```

    MDS 在两次上报时保存 `image_id/disc_id -> node_id` 的所属关系，因此不需要在每个文件中重复保存 `node_id`。

    这里描述的是逻辑数据关系，不规定这些字段如何编码、组合或写入 KV。

    ## 6. 完整流程

    ```text
    MDS 选择目录子树
        |
        | SendArchiveMetadata（可分片）
        v
    光盘库节点收齐文件信息
        |
        | AllocateAvailableImageId
        v
    MDS 分配 image_id
        |
        | 光盘库节点读取文件并生成镜像
        v
    ReportFilesPackedToImage
        v
    MDS：文件状态 = ARCHIVE_IMAGE_READY
        |
        | AllocateAvailableDiscId
        v
    MDS 分配 disc_id
        |
        | 光盘库节点将镜像刻录到光盘
        v
    ReportImagesBurnedToDisc
        v
    MDS：文件状态 = ARCHIVE_COMPLETED
    ```

    整个流程共有五个接口：一个文件信息下发接口、两个 ID 分配接口和两个阶段上报接口。

    ## 7. 与底层实现解耦

    接口只使用 `node_id`、`node_address`、`allocate_ts_ms`、`batch_id`、`inode_id`、`size`、`object_unit_size`、`target_node_id`、`target_disk_id`、`image_id` 和 `disc_id`。

    接口不包含目录结构、文件路径、RocksDB key、Masstree page、PG、副本、extent 或路径路由结果。文件内容由光盘库节点根据 `target_node_id`、`target_disk_id` 和 `inode_id` 从热数据节点下载，MDS 不参与内容传输。MDS 始终根据 `inode_id` 更新归档信息。因此更换 KV 引擎和路径解析方法时，不需要修改这些 RPC。

    ## 8. 后续实现和验证

    本次只更新设计文档，不在 MDS 中增加归档代码。后续最小实现顺序为：

    1. 定义 `ArchiveFile` 和 `OpticalNodeService`。
    2. 在 MDS protobuf 中增加两个 ID 分配 RPC 和两个上报 RPC。
    3. 实现 ID 分配接口、第一次上报和第二次上报。
    4. 实现 MDS 的定时选择和分片发送流程。

    第一版只验证一个正常场景：MDS 分片发送一批文件信息；光盘库节点向 MDS 申请 `image_id`，完成镜像制作和第一次上报；随后申请 `disc_id`，完成刻录和第二次上报；最终所有文件均为 `ARCHIVE_COMPLETED`。

    ## 9. 暂不设计的内容

    以下内容等出现实际需求后再扩展：

    - 归档期间的读写、删除、移动和重命名。
    - 超时、失败、重试、幂等、补传和任务恢复。
    - 多批次并发、任务租约和节点重派。
    - 文件、镜像或光盘副本以及 PG。
    - 文件跨镜像切分。
    - 在光盘库中保存原有目录结构和目录元数据。
    - 完整性校验、刻录失败和损坏介质处理。
    - 权限、审计、配额、ACL、xattr、硬链接和稀疏文件。
